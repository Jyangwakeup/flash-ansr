# 历史精修实验规则

版本：v1　日期：2026-11-21　状态：开跑前锁定

本文规定历史精修实验怎么评测、怎么比较。规则在看到中等规模和正式规模的结果之前写定，跑完以后不能改成对结果更有利的算法。实验设计见 [设计.md](设计.md)，工程试跑结果见 [试跑报告.md](试跑报告.md)。

每条规则都注明来源：

- **【沿用原方案】**：原 Flash-ANSR 代码或已有基线实验已经这样做，本实验照抄。
- **【本实验新定】**：原方案没有对应做法，按设计.md 的要求补定。

中等规模和正式规模共用同一套规则，只有运行参数不同（见第 9 节）。

---

## 1. 怎么算解对【沿用原方案】

**在留出点上，FVU ≤ float32 的机器精度（约 1.19×10⁻⁷），才算解对。**

- FVU = 预测误差的平方均值 ÷ 观测值的方差，也就是 1 − R²。0 表示完全拟合，越小越好。
- 方差用 float64 计算。阈值是 `numpy.finfo(numpy.float32).eps`。
- 来源：`experiments/baseline_scaling/run_baseline.py` 第 103–107 行，与 srbf 的 `is_perfect_fit` 口径一致。
- 留出点不参与公式生成、常数拟合和候选排序，只用来判断对错。
- 这是数值标准，不等于公式和答案在符号上完全相同。

每道题记两个结果：

| 指标 | 含义 |
|---|---|
| Oracle | 所有候选里，有没有至少一个解对 |
| Top-1 | 按排序规则排第一的候选，有没有解对 |

排序沿用原默认 `ranking="mdl"`【沿用原方案】。

不使用"误差小于 0.001"这类自定阈值。阈值确定后不再更改。

## 2. 怎么比才公平【本实验新定，比较口径来自设计.md §7】

两种比较都要做，都要报告。

### 2.1 同样的生成次数

- 第一阶段：冻结的原 T8 每题生成 300 次。直接复用验证题的模型候选池，不重新生成。
- 第二阶段：各组训练后的模型每题再生成 700 次。
- 两阶段合并排序，对照"原 T8 在同一批题上直接生成 1000 次"。
- 对照必须用相同的题目、数据种子、拟合设置和解对标准。已有的 baseline_scaling 基线用的是另一批题（fastsrb 120 题），只能当参考，不能直接拿来对比。

### 2.2 同样的时间

给历史的生成比较慢，因为前面多了历史公式，所以要另做一次时间相同的比较。

1. 先在验证集上实测每种方案每题实际耗时。
2. 按实测结果定好每题的总时间预算，以及两个阶段各分多少。
3. 计时范围固定为：数值编码、挑选历史、生成公式、拟合常数，四项都计入。离线建池的时间单独报告，不算进每题耗时。
4. 时间比较只在同一台机器、同样的线程数下进行。
5. 预算定下来后，所有方案都用同一个预算，不再调整。

在完成同时间比较之前，结论只能写成"生成次数相同时更好"，不能写成"花同样的计算更好"。

## 3. 坏题怎么处理【本实验新定，拟合流程沿用原方案】

- **所有题都留在分母里**，不删题，不换题。
- 拟合沿用原 Refiner 流程：拟合失败的候选不保留，全部失败时返回空池（`on_empty="return"`）。不做额外的数值修复。
- 训练时抽到空池的题，退回 K=0（不给历史），单独统计次数。
- 评测时某道题没有任何可用答案，**记为没解对**。不能因为退回 K=0 就当成解对。
- 第 40 题这类数值溢出的题，按上面的规则处理。
- 如果以后修改数值处理，所有组必须一起改，并且重新跑。

## 4. 用哪一步的模型【本实验新定】

- **主结果只用最后一步的模型**：中等规模用第 1,000 步，正式规模用第 10,000 步。
- 中途保存的 checkpoint 只用来画变化曲线，不能从中挑分数最高的当结果。
- 最终测试集（已有的 test）只在规则锁定后跑一次。不能用它挑 checkpoint、调参数或决定训练规模。

## 5. 种子和数据划分【本实验新定】

### 5.1 种子是什么，为什么要固定

种子是随机数的起点。程序里很多步骤需要随机抽取，例如出题、挑历史、生成公式。种子不变，每次运行的随机结果就完全相同，别人照着跑也能得到同样的结果。种子一改，题目和抽样都会变，前后结果就不能比较。

### 5.2 五个种子

| 种子 | 值 | 用在哪里 | 例子 |
|---|---|---|---|
| 训练题数据种子 | 20261121 | 生成训练题：随机选公式、取 X、加噪声 | 第 1 道题是 `y = sin(x1) + 2x2`，X 取这 460 个点 |
| 验证题数据种子 | 20261122 | 生成验证题 | 和训练题用不同的种子，两批题才不会一样 |
| 训练种子 | 20261123 | 每一步抽哪 128 道题、给不给历史、给的话挑池里哪个候选、condition dropout | 第 5 步抽到第 37 题，给历史，挑了池里第 3 个候选 |
| 拟合种子 | 20261124 | 常数拟合从哪个初始值开始猜（建池和评测都用） | 公式 `c·x1 + c`，第一次从 c = 0.8 开始调 |
| 评测种子 | 20261125 | 评测时模型生成公式的随机采样 | 第 10 题生成的 700 个公式具体是哪些 |

数字本身没有含义，是接着试跑用的 20261120 往后编号的。

### 5.3 使用规则

- **种子写进运行配置文件**（格式仿照 `experimental/history_benefits/pilot.yaml`），运行开始后不再改动。每次运行的输出目录里保存一份实际用到的配置。
- **A/B/C 三组用同一个训练种子**。三组每一步抽到的题相同；B、C 每一步给不给历史的抽签结果也相同。这样三组的差别只剩"有没有历史、历史从哪来"。
- **五个种子分开**。试跑只用一个总种子，再派生出各环节的随机数；正式实验拆成五个，改一个环节不会连带改动别的环节。例如只想重新评测，换评测种子就行，训练题和训练过程不变。
- **换种子要记录**。如果以后想多做几次独立重复（例如每组用 3 个训练种子），新种子要写进修改记录，结果按种子分开报告，不能只挑结果好的那个。
- **中等规模和正式规模用同一组种子**。这样中等规模的题目和候选池在扩大规模时可以直接复用。如果实际实现做不到（例如扩题以后前 1,000 道题变了），开跑前要检查清楚并记录。

### 5.4 数据划分

- 题目来源：`configs/v25.0-T8.1-3M` 的 catalog 和 sampling 配置。
- 训练题和验证题用不同的数据种子，开跑前检查有没有重复的题，重复的要记录。
- 最终测试用已有的 test 集，不参与训练、选模型或调参数。
- A/B/C 三组共用同一批训练题和验证题。

## 6. 统计方法【本实验新定】

- **同一道题配对比较**：比较两种方案时，看的是同一批题上两者成功率的差。
- **置信区间**：按题目做 bootstrap 重抽样 10,000 次，报告差值的 95% 置信区间。
- 每个结果都写明题数、种子数和分母。
- 同一道题用多个种子重复跑，不能当成多道独立的题。
- 设计中 H4 的"效果接近"定义为：同样给模型历史的情况下，B 减 C 的成功率差，95% 置信区间下限不低于 −3 个百分点。

## 7. 其他实现规则【本实验新定，对应设计.md §2.4 的待定项】

| 待定项 | 规定 |
|---|---|
| 历史 token、标记位置、目标提取 | 沿用试跑已验证的实现，正式运行前记下代码的 git 版本 |
| 历史加目标太长 | 上限 256 个 token（历史前缀加最多 128 个目标 token）。超长的样本记录下来，退回 K=0，不截断公式，不删题 |
| condition dropout | 沿用试跑做法：触发 dropout 时，历史公式和历史预测一起去掉，单独计数 |
| 同结构缓存 | 主结果不用缓存，每个候选都重新拟合。缓存命中情况另外记录，不算进主结果 |
| 选 checkpoint | 只用最后一步（见第 4 节） |
| 配对置信区间 | 见第 6 节 |
| H4 容许差距 | 3 个百分点（见第 6 节） |

## 8. 开跑前提条件【本实验新定】

1. **迁移对照**：在同一批验证题上，用相同的生成次数和评分方式，比较三个模型：原 T8、开启修复后的起点（step-0）、A 组最后一步。目的是看 T8.1 的修复有没有让模型变差，以及训练后能恢复多少。中等规模的最终评测要包含这一项。
2. 如果修复后的起点明显变差，而且 A 组训练后也没能恢复，就**先停下来讨论**，不直接扩大规模。
3. 本文提交到 git 后才开跑。之后如果要改，必须在文末"修改记录"里写明原因，并注明是在看到哪些结果之前还是之后改的。

## 9. 运行参数

### 9.1 中等规模（先跑这个）

| 项目 | 设置 |
|---|---|
| 题目 | 1,000 道训练题 + 200 道验证题 |
| 候选池 | 每题每种来源生成 300 次，最多保留 16 个，完整格式保存（约 140 MB） |
| 训练 | A/B/C 各 1,000 步，每步 128 个样本，共 12.8 万个样本，平均每道训练题用约 128 次 |
| 学习率 | 前 100 步从 0 升到 1e-4，之后保持 1e-4 不降 |
| 保存 | 每 200 步保存一次完整 checkpoint，包括权重、优化器、学习率进度、随机数状态、样本位置，可以接着训 |
| 中途评估 | 每 200 步：200 道验证题的验证 loss，加每题生成 20 次的 Oracle 和 Top-1。只用来画曲线 |
| 最终评测 | 第 1,000 步，按第 2 节的规则；加第 8 节的迁移对照 |

**中等规模的结果只用来判断方向**，决定要不要扩大到正式规模，不能当作正式结论。第 1,000 步的结果要标注"学习率未降"。

**接着训到正式规模**：可以从第 1,000 步的 checkpoint 直接接着训，学习率按正式计划继续。如果训练题从 1,000 道扩到 1 万道，要在运行记录里写明从哪一步开始换题。中等规模的候选池，只要生成设置和种子不变，可以直接复用。

### 9.2 正式规模

| 项目 | 设置 |
|---|---|
| 题目 | 10,000 道训练题 + 1,000 道验证题 |
| 候选池 | 同中等规模 |
| 训练 | A/B/C 各 10,000 步，每步 128 个样本 |
| 学习率 | 前 100 步升到 1e-4，保持到 8,000 步，在 10,000 步时降到 0 |
| 保存 | 每 1,000 步，只用来画曲线 |
| 最终评测 | 第 10,000 步，按第 2 节的规则 |

## 10. 运行预算和机器

### 10.1 耗时估算

本机（Apple M4，CPU，4 个并行）的估算按试跑速度推算：每题每种来源生成并拟合 300 次约 5 秒，每步训练约 6 秒。GPU 一栏没有实测。

| 环节 | 中等规模，本机 | 正式规模，本机 | 正式规模，GPU 服务器（估算） |
|---|---|---|---|
| 建池 | 约 3.4 小时 | 约 31 小时 | 约 4–8 小时（16–32 核 CPU） |
| 训练（三组合计） | 约 5 小时 | 约 51 小时 | 约 1–3 小时 |
| 中途评估 | 约 1 小时 | 另算 | 另算 |
| 最终评测 | 约 5–7 小时 | 另算 | 主要靠 CPU |
| 合计 | **约 15–16 小时** | 82 小时以上 | 约半天到一天 |

建池和评测主要花在 CPU 拟合常数上，GPU 帮不上忙。**选机器主要看 CPU 核数**，GPU 只能缩短训练这一项。

### 10.2 机器方案（正式规模，待定）

| 方案 | 做法 | 注意 |
|---|---|---|
| 学校或实验室的 GPU 服务器 | 建池用多核 CPU 分片并行，训练用 GPU | 原作者就是在 GPU 服务器上训练的 |
| 租云 GPU | 按小时计费 | 选 CPU 核数多的机型 |
| 本机 Mac | 训练可以试 MPS 加速，建池分片跑，中断后能接着跑 | 总共约 3–4 天 |

无论选哪种，先在目标机器上跑一小段（建 50 道题的池、训练 100 步），用实测速度替换上面的估算，再正式开跑。

**换机器不改变规则**：同一规模的 A/B/C 三组必须在同一种设备上跑完；时间比较只在同一台机器上做。
